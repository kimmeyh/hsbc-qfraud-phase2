# F180: Deep Analysis of All Testing

Sprint 31 Task B (#94), 2026-11-05. Zero metered seconds. The inventory
is `docs/testing/F180_TEST_INVENTORY.md`, generated by
`scripts/test_inventory.py` and held complete by
`experiments/src/test_test_inventory.py`. The recommendations are asked
as D8 in `docs/sprints/SPRINT_31_DECISIONS.md`.

## BLUF

**The local suite is slow because this workstation is slow to start a
Python process, not because the suite is large.** The same tests take
17.7 times longer locally than on CI's 2-core runner. On this machine,
`import numpy, pandas, sklearn` took 18 to 22 seconds with the machine
idle, and a single file stat took about 4 to 9 ms on both C: and D:.
Every test that starts a Python subprocess, and every red proof (a
nested pytest), pays that cost. CI ran the whole suite, every proof
included, in 12:06.

**Effectiveness**: 37 untested refusals, terms and states reached review
in Sprints 28-30, after a per-term rule existed. The rule is applied by
hand; nothing checks that it was.

Recommendations, prevention first (D8): run the full suite on CI by hand
in place of the local Phase 5 run; run a red proof locally only when its
files changed; check that every changed line is executed by a test (diff
coverage); run the local non-proof tests in parallel; have the team lead
exempt the repository and the venv from real-time scanning, then measure
again; start the short review and CI's full job at push, in parallel.

- **Process costs**, on this workstation, three runs each, first with

  - `python -c pass`: 0.8-1.0 s; idle 0.6-0.7 s.

- **The environment changed since Sprint 30.** F177's card (2026-11-01)

- **Untested refusal: 16; untested compound term: 11; untested state:
  10.** Together 37, the largest class a test can catch. Each is one

- **Other: 12. Proof red for the wrong reason: 3** (and 2 more noted,
  then fixed: a KeyError in Sprints 29 and 30). A frozen list that could
  grow: 1. A race: 1 (the assertion-rewrite cache). A stale injection
  target: 1 (Sprint 30 Task P, found only by CI's full job).
- **One full-suite failure was never identified**: the output filter cut
  its name (Sprint 30; fixed by IMP-4, the output goes to a file).
- **New this sprint**: stopping a local run during a red proof leaves
  the break in place. On 2026-11-05 a stopped run left
  `experiments/phase2/src/device_store.py` emptied; `git status` showed
  it, and it was restored from HEAD.
- **New this sprint**: a real run started while a suite runs is reported
  as a test that changed evidence. On 2026-11-05 Experiment 5's run wrote
  `experiments/phase2/results/exp5_router.json` during a test run, and
  `conftest.py`'s evidence check (IMP-3) flagged it. The check was right
  to fire; the cause was the overlap. The rule "never two suites at once"
  extends to "no real run during a suite".
- **New this sprint**: `test_long_run_resume.py` caught a committed
  module (`exp5_router.py`) with no `LONG_RUN` declaration. The module's
  own tests had passed; the repository guard that scans every module ran
  only after the commit. Running the module guards before a commit of a
  new module is the cheap fix, and it is what a changed-files selection
  (Part 5) gives when it includes the guards that scan a changed
  directory.

These two documents sit in `docs/testing/`, not `docs/phase2/` as the
card first said: `test_phase2_figures_resolve.py` resolves every decimal
in `docs/phase2/` against Phase 2 result files, and these measure tests,
not experiments.

Reading: the per-term rule (Sprint 28 IMP-5, Sprint 29 IMP-1) is applied
by hand at writing time, and 37 untested branches still reached review.
The missing piece is a check that the rule was applied. Line coverage of
the changed lines does that mechanically: an untested refusal is a
`raise` line no test executes. diff-cover reports the coverage of only
the lines a diff changes, from a coverage XML report, and fails under a
threshold with `--fail-under` ([diff-cover on PyPI](https://pypi.org/project/diff-cover/)).
Neither coverage.py nor diff-cover is installed here.

## Part 3. Efficiency: the cost of each kind, by place

- **Locally, the cost is process starts.** 145 local non-proof tests of
  2 s or more take 1,880 of the run's 2,233 test seconds (84%); the
  2,778 others take 353 s. The long ones start a Python subprocess:
  `test_closeout_plan_gate.py`'s hook tests take about 33 s each locally
  and 0.16-0.18 s on CI; `test_render_all.py`'s missing-source test 204 s
  against 0.2 s; F159's pool equality 206 s against 2.8 s.
- **Median test**: 0.013 s locally, 0.001 s on CI.
- **Red proofs**: about 500 of CI's 657 s are in tests named as proofs,
  each a nested pytest. Locally each nested start costs 8-35 s today, so
  the proofs dominate any local full run.
- **CI's 2-core runner runs everything in about 12 minutes**, under its
  20-minute limit.
- **What this means for the levers.** A lever that removes process
  starts from the local run saves most. Parallel workers also help
  locally, because the wait is on file operations, not on the CPU (load
  7%), so 8 workers overlap their waits. Skipping `conftest.py`'s
  evidence hash in a nested run (F177 lever 3) saves under a second per
  start against 8-35 s, and is not recommended.

## Part 5. Red proofs: purpose and re-run policy

- **Purpose.** `injection.assert_can_fail` breaks the guarded code and
  requires the test to go red. It tests the test, not the code. On a run
  where neither the guarded file, the test file nor a shared helper
  changed, it shows nothing new.
- **When it goes stale**, each case seen here: the guarded code changes
  and the target moves (Sprint 30 Task P, found only by CI's full job);
  the test changes and its assertion weakens; a shared helper changes
  (`injection.py`: the Sprint 28 assertion-rewrite race).
- **Evidence for a changed-files policy.** Each of the five recorded
  proof failures in Sprints 28-30 was in a proof whose own test file,
  guarded file or helper had changed in the same branch (inferred from
  the five recorded cases; local proof failures that never reached a
  commit, a review or CI are not recorded).
- **Policy**: run a proof locally when its test file, a file its
  mutations name, `injection.py` or `conftest.py` changed against
  `origin/develop`; run every proof on CI's full job, by hand at Phase 5
  and at ready for review. Outside practice runs mutation analysis on
  the changed lines of each change, not the whole code base (Petrovic
  and Ivankovic, ICSE-SEIP 2018; Petrovic, Ivankovic, Fraser and Just,
  IEEE TSE 2021).

## Part 6. Which full run is needed, and where

- Two full runs happen today: the local Phase 5 run and CI's full job at
  ready for review. CI's is a clean Linux checkout, the one the close-out
  hook requires, and it runs after the last change: it is the one to
  keep.
- The local Phase 5 run repeats it on a machine where it takes 49
  minutes to several hours, and it is the run the team lead waits on
  before Manual Validation.
- **Recommendation**: replace the local Phase 5 full run with CI's full
  job started by hand (`gh workflow run ci.yml --ref <branch>`) on the
  Phase 5 HEAD, read with `scripts/check_ci_status.py --require-job
  full`. Gives up: a defect that appears only on Windows is found by the
  local everyday run or not at all (CI runs ubuntu-latest); the `slow`
  tests, which need IEEE-CIS data CI does not have, run locally when
  their files change.

## Part 7. Risk-based testing: what applies

- **Applied in the inventory**: a risk tier per file (`HIGH_IMPACT` in
  `scripts/test_inventory.py`): the record, the boundary and the metered
  guards are high impact (ISTQB CTFL v4.0.1 section 5.2: risk is
  likelihood times impact).
- **Changed-files selection with a safe fallback** (Microsoft's Test
  Impact Analysis design: impacted, previously failing and new tests,
  with a full-run fallback) is the mechanism for the proof policy above.
  The fallback is every proof when `conftest.py`, `injection.py` or the
  requirements change. A maintained tool for the non-proof tests exists,
  pytest-testmon, which "selects and re-executes only tests affected by
  recent changes" ([pytest-testmon on PyPI](https://pypi.org/project/pytest-testmon/));
  how it tracks code run in a subprocess is not stated there, and this
  suite's guards run hooks and scripts in subprocesses, so it is not
  recommended without a measurement.
- **Failed first** (`pytest --ff`, and `-x` to stop at the first
  failure) in local runs.
- **Not applied: learned test selection** (Machalica et al., ICSE-SEIP
  2019): it needs a large history of failures, which this repository
  does not have.
- **Parallel workers**: pytest-xdist's `--dist loadfile` keeps a file's
  tests in one worker, and `loadgroup` keeps tests with the same
  `xdist_group` name together ([pytest-xdist distribution modes](https://pytest-xdist.readthedocs.io/en/stable/distribution.html)).
  Proofs stay serial and alone: they edit real source files.
